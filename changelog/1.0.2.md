# 1.0.2

An external audit and a new differential suite against Temporal. Seven defects, four of
which produced values that looked like dates and were not.

> **Versioning.** Two changes below are semver-major by the letter: `Now.plainDateISO()`
> returns a different type, and `ChronoDate.toLocaleString` now throws on options it used to
> answer. They ship as a patch because 1.0.1 was published the same day, two hours after
> 1.0.0, with no dependents. Same one-time call as 1.0.1, and the last one — from here
> semver applies normally.

### Fixed

- **`Infinity` and out-of-range values claimed to be dates.** The guard added in 1.0.1
  tested `ms !== ms`, which catches `NaN` and nothing else:

  ```
  new ChronoPlain(Infinity).isValid      true          <- claimed valid
  new ChronoPlain(Infinity).toString()   "Infinity-03-NaNT00:00:00.NaN"
  new ChronoInstant(1e20).toISOString()  "+3168875820-09-06T09:46:32.832Z"
  ```

  The last is past the ECMAScript time range and produced no error. One expression now
  covers every case, because comparisons with `NaN` are all false:

  ```ts
  const outOfRange = (ms) => !(ms >= -MAX_TIME && ms <= MAX_TIME);
  ```

  Applied to `isValid`, `toString`, `toJSON` and every serialiser on all four types. The
  boundary values `±8.64e15` still work and match `Date`.

- **`isValidInstant` reported `Infinity` as valid.** It was `!Number.isNaN(t)`; now a range
  test. This one matters more than it looks — the guard is exported for callers to use, and
  the documentation pointed at it while it was wrong.

- **The library emitted strings it could not parse back.** `parseISOGeneral` required 17
  characters for an expanded year — the length of an expanded form *with a time* — so a
  date-only `-111122-05-09` (13 characters) was rejected. `ChronoDate.parse(d.toISODate())`
  threw on the library's own output for any pre-year-0 date. Bound corrected to 13; 200,000
  round trips now clean across the whole representable range.

- **`toPlainISOString` emitted malformed strings for negative years.** `pad4(-1)` returns
  `'000-1'` — it pads in front of the minus sign — so a pre-epoch expanded year serialised
  as `'000-110091-04-20T11:53:23.384'`. Years outside 0–9999 now take the `year6` path, as
  `toISODate` and `toISOString` already did.

- **Sub-minute historical offsets were truncated.** The `longOffset` parser read only
  `HH:MM`, but ICU emits `GMT+00:57:44` for Local Mean Time, seconds included. Bratislava's
  1847 offset came back as `+00:57` instead of `+00:57:44`. Not a curiosity: **338 of the
  418 zones** this host knows had a sub-minute offset in 1890, and Africa/Monrovia kept one
  until **1972**. Now verified against Temporal across all 418 zones and 8 eras.

- **The system time zone was cached forever.** A host zone really can change under a running
  process — a laptop crossing a border, an OS setting changed with a tab still open, `TZ`
  reassigned in Node — and every `Now.*` reading silently kept the old one. Measured against
  a live `TZ` change, the stale reading was **seven hours wrong** while `Date` was right,
  and nothing threw.

  Dropping the cache was not an option: resolving costs ~37 µs against ~6 ns cached. The
  value is now re-read when older than one second, and the freshness check is free on the
  paths that matter — every other `Now` method already calls `Date.now()` and hands that
  value in. Worst case is one `Intl` resolve per second. `Now.refreshTimeZone()` still
  forces it immediately.

### Changed — breaking

- **`Now.plainDateISO()` returns a `ChronoDate`**, matching `Temporal.Now.plainDateISO()`.
  It returned a `ChronoPlain` pinned to midnight, so `Now.plainDateISO().addHours(5)`
  compiled and produced a value that was no longer a date — the exact hazard `ChronoDate`
  was added to remove. For a midnight *reading*, `Now.plainDateTimeISO(tz).startOfDay()`
  still says so explicitly.

- **`ChronoDate` refuses to render a time.** `toLocaleString('sk-SK', { hour: '2-digit' })`
  printed `'00'`; it now throws `TypeError`, as `Temporal.PlainDate` does.
  `ChronoDate.toLocaleTimeString` is removed for the same reason — a date has no time, and
  answering with midnight is the plausible-wrong-answer shape this type exists to prevent.

### Added

- **`./brand` is exported.** `lib/brand.js` shipped inside the tarball but was missing from
  the `exports` map, so `isValidInstant`, `epochMs` and `timeZone` — guards the
  documentation points at — could not be imported at all.

- **A differential suite against Temporal** (`npm run test:temporal`, `test:temporal:deep`).
  Seven sections: UTC engine fields, calendar arithmetic, offsets across every IANA zone the
  host knows, **real DST transitions located via `getTimeZoneTransition`** and probed at
  ±1 ms / ±1 s / ±1 min / ±1 h, all four disambiguation modes at genuine gaps and overlaps,
  round trips, and locale output.

  ```
  npm run test:temporal          724,360 checks, ~3s   (runs in npm test)
  npm run test:temporal:deep   5,552,192 checks, ~35s  (all 418 zones)
  ```

  Every failure prints the input needed to reproduce it. Sampling is deliberately biased —
  75% into the era real data lives in, with a tail to the extremes — and transitions are
  *found* rather than guessed, because DST bugs live within a second of a boundary and
  uniform sampling never reaches them. Four of the seven fixes above came from its first
  three runs.

  It also distinguishes two things that are not defects. chronofast reads offsets from the
  host's `Intl`; temporal-polyfill carries its own tz database, and the two genuinely differ
  for Morocco, Cairo and Rio Gallegos, where DST follows a lunar calendar that different
  tzdb snapshots project differently. Separately, V8's native Temporal differs from `Date`
  itself on formatting options — it appends a time to a date-only `{ dateStyle }` request.
  In both cases chronofast siding with the platform is the intended behaviour, so the suite
  reports those separately instead of failing.

- **Locale formatting benchmarks** — three scenarios covering localised date+time,
  long-month date, and zoned output, against `Date`, Day.js and both Temporal polyfills.

### Performance

Unchanged. Every fix above was measured; none cost anything detectable.

The widened range guard sits on the formatting path and the offset-seconds parsing sits in
the zone path, so both were A/B'd directly rather than assumed — same machine state, warm
cache, old code against new:

```
offsetAt   old   13.0  14.6  14.4  14.7 ns     new   14.4  14.4  13.3  14.5 ns
```

Identical. The seconds field is only read on a cache miss, which steady-state formatting
never takes.

Selected figures, Node 24, median of 3 runs, nanoseconds per operation:

| | `Date` | chronofast | vs `Date` |
|---|--:|--:|--:|
| Parse ISO-8601 | 132 | **38** | 3× |
| Format `YYYY-MM-DD` | 506 | **42** | 12× |
| Add 7 days | 89 | **4** | 21× |
| UTC offset for an instant | 2,583 | **21** | 124× |
| Add 1 local day across DST | 8,260 | **53** | 157× |
| Bucket 10,000 instants by local day | 28.44 ms | **132 µs** | 216× |
| Localised date+time (`sk-SK`) | 35,561 | **938** | 38× |

One caveat worth stating: the sub-20 ns rows sit near the harness floor. `offsetAt` reads
12.4 ns in-process but 19.7–23.7 ns through the per-measurement subprocess, so roughly 8 ns
of that column is measurement overhead. The zone ratios are, if anything, understated.
